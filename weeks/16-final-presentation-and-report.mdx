최종 발표와 보고서는 무엇을 물었고, 어떤 자료와 판단으로 분석했으며, 어디까지
결론낼 수 있는지 연결한다. 아래는 준비용 구성안이다. 발표 시간·제출 기한·파일 형식,
상세 채점 기준과 Quiz 3의 문항·배점은 별도 공지를 따른다.

## 1. 보고서와 발표의 공통 뼈대

| 구성 | 포함할 근거 |
|---|---|
| 문제 | 사용자·결정·연구 질문·적용 범위 |
| 자료 | 출처·이용 조건·측정·표본·누락·윤리 검토 |
| 방법 | cleaning·전처리·분할·baseline·선택 절차 |
| 결과 | 고정 평가 지표·분모·단위·변동·실패 사례 |
| 안정성 | 실제 비교한 판단 대안과 유지되거나 바뀐 결론 |
| 해석 | 관측 관계·prediction·인과 주장의 구분 |
| 활용과 한계 | 가능한 사용, 보류·중단 조건, 미확인 대상 |
| 재현 | commit·환경·실행 명령·자료 접근·결과 파일 |

발표에서는 핵심 주장과 그 근거를 읽을 수 있게 고르고, 보고서에는 검토에 필요한
세부 방법과 결과를 남긴다. 기대와 맞지 않은 결과도 보고한다. 탐색·군집화 프로젝트는
정답 없는 구조에 accuracy를 억지로 붙이지 않고 외부 대조와 안정성 근거를 설명한다.

## 2. 최종 숫자를 확인하기

예를 들어 MAE(mean absolute error)가 3.5분에서 2.8분으로 줄었다면 오차의 평균이
0.7분 작아진 것이다. 실제 대기가 0.7분 줄었다는 운영 효과로 표현하지 않는다.
날짜마다 개선 방향이 달랐다면 평균과 날짜별 차이를 함께 보여 준다.

독립 test를 남기지 못했거나 결과를 본 뒤 수정했다면 그 과정을 공개한다. Validation
점수를 독립 최종 성능으로 바꾸어 부르지 않는다. 이런 구분은 VDS가 강조하는
모델 선택과 최종 평가의 분리에 해당한다.[^vds13]

## 3. 최종 점검

1. 발표·보고서·코드 결과의 숫자와 version이 일치하는가.
2. 표·그림에 기간·단위·분모·출처가 있는가.
3. 중요한 판단 대안과 실패 결과가 빠지지 않았는가.
4. 재실행 방법과 공개할 수 없는 자료의 접근 조건을 구분했는가.
5. 외부 자료의 출처·재사용 조건과 저장소의 비공개 정보 노출을 확인했는가.

프로젝트의 기여는 점수 향상뿐 아니라 기존 질문이 왜 답하기 어려웠는지 밝힌 결과나,
더 타당한 측정·평가 절차를 만든 결과일 수도 있다. 실제 확보한 근거에 맞춰 기여를 쓴다.
