Demo는 사용자가 결과를 얻는 과정을 실제로 따라가 보는 시간이다. 웹 앱이 필수라는
뜻은 아니다. 분석 notebook, 명령행 pipeline, 보고서 생성 과정도 프로젝트 목적에 맞으면
입력부터 결과까지 시연할 수 있다. 시연 시간·제출 방식은 별도 공지를 따른다.

## 1. 하나의 사용 장면을 정하기

| 단계 | 시연 내용 |
|---|---|
| 상황 | 누가 어떤 결정을 하려는가 |
| 입력 | 필요한 자료, 형식, 정보의 마감 시각 |
| 실행 | 고정된 코드·모델·설정으로 결과 생성 |
| 출력 | 값·단위·불확실성·적용 범위를 함께 표시 |
| 판단 | 결과를 어떻게 사용하고 언제 보류하는가 |

식당 예측이라면 11:30에 이용 가능한 입력만 넣고 12시 구간의 예측을 보여 준다.
과거 기록을 재생하는 경우에는 실시간 운영 결과와 구분한다. 사전 계산한 결과를
보여 준다면 계산 시점과 사용한 version을 표시한다.

## 2. 실패 상황도 시연하기

정상 입력과 함께 프로젝트에 실제로 중요한 실패 사례를 고른다. 새 식당, 필요한 값의
누락, 잘못된 단위, 모델의 적용 범위를 벗어난 입력 등이 후보다. 입력을 거부하거나
사람에게 넘기는 조건을 설명하고, 실패를 정상 prediction처럼 표시하지 않는지 확인한다.

네트워크나 외부 API(application programming interface)에 의존한다면 연결 실패 시
보여 줄 기록이나 재현 가능한 예제를 준비한다. Demo 자료에는 비밀 키나 비공개
개인정보를 포함하지 않는다.

## 3. 재현과 피드백 기록

새 세션에서 실행 명령을 따라 결과를 생성해 본다. 필요한 환경, 데이터 접근 방법,
commit, 실행 시간과 결과 파일을 기록한다. 시연 후에는 발견된 문제를 사용 흐름,
계산 오류, 자료 문제, 해석 문제로 구분해 담당자와 수정 확인 방법을 정한다.

시연이 성공했다는 사실은 새로운 독립 평가를 통과했다는 뜻이 아니다. 모델 성능 주장은
고정된 평가 protocol과 그 결과로 뒷받침한다.
