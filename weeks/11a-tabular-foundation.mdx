9주차에는 선형회귀로 펭귄 몸무게를, 10주차에는 로지스틱 회귀와 트리 앙상블로 Chinstrap 여부를 예측했다.
트리 앙상블은 몸무게 같은 연속값에도 그대로 쓸 수 있으니, 이번 주는 몸무게 예측으로 돌아와 선형회귀와 XGBoost를 한자리에 모은다.
XGBoost를 트리 앙상블의 대표로 두었지만 랜덤 포레스트도 같은 방식으로 더할 수 있다.
이 후보들은 모두 지금 가진 훈련 데이터만 보고 매개변수를 맞추고, XGBoost라면 트리의 깊이와 개수 같은 초매개변수도 검증으로 골라야 한다.
**TabPFN**(Tabular Prior-data Fitted Network)은 방식이 다르다.[^tabpfn]
수많은 가상의 표 문제로 미리 학습해 두고, 새 표를 만나면 그 표의 훈련 행을 입력으로 받아 곧바로 예측한다.
이처럼 대규모 사전학습으로 여러 문제에 두루 쓸 능력을 얻은 모델을 **파운데이션 모델**(foundation model)이라 부른다.

TabPFN v2 논문은 1만 행 이하의 표에서 초매개변수 탐색 없이 기본 설정만으로 기존 방법을 앞섰고, 분류에서는 평균 2.8초 만에 4시간 튜닝한 부스팅 등 기존 방법들의 앙상블보다 좋았다고 보고했다.[^tabpfn]

## 1. 모델을 맞추는 두 방식

XGBoost는 `fit`에서 이 표의 훈련 행에 맞춰 트리를 쌓고, 다른 표를 만나면 처음부터 다시 쌓는다.
TabPFN은 가중치를 사전학습에서 한 번 맞춘 뒤 새 표에서는 바꾸지 않는다.
이 표의 훈련 행은 여전히 필요하지만, 예측할 행과 함께 입력으로 들어간다.

| | XGBoost | TabPFN |
|---|---|---|
| 가중치를 맞추는 자료 | 이 표의 훈련 행 | 사전학습에 쓴 수백만 개의 합성 표 |
| 이 표의 훈련 행이 쓰이는 때 | `fit`에서 트리를 만들 때 | `predict` 때 예측할 행과 함께 |
| 초매개변수 | 검증으로 고른다 | 기본값을 그대로 쓰는 경우가 많다 |
| 계산이 몰리는 때 | 학습 | 예측 |

## 2. TabPFN의 사전학습과 예측

### 2.1 합성 데이터 사전학습

TabPFN의 사전학습 자료는 실제 데이터가 아니라 컴퓨터가 만든 **합성 표**(synthetic dataset)다.
합성 표 하나가 예측 문제 하나다.
무작위로 정한 생성 규칙으로 특성을 만들고 그 특성에서 결과를 만들기 때문에, 어떤 표는 입력과 결과가 거의 직선 관계이고 어떤 표는 곡선이나 임계값을 가지며, 잡음의 크기도 표마다 다르다.
이런 생성 규칙들이 어떤 분포에서 뽑히는지를 정한 가정이 **사전분포**(prior)다.
Prior-data Fitted Network라는 이름은 "사전분포에서 뽑은 표들로 맞춘 신경망"이라는 뜻이다.

학습 과제는 각 합성 표에서 일부 행의 정답을 가리고, 나머지 행의 특성과 정답을 보고 가린 정답을 맞히는 것이다.
가린 정답에 대한 예측이 틀린 만큼 손실을 매기고([10a §1.3](/lecture/2026f-applied-data-science/10a-binary-classification#13-로그-손실과-학습)의 로그 손실과 같은 형태), 그 손실이 줄도록 가중치를 갱신한다.
이 과정을 수백만 개의 표에서 반복하면, 모델은 특정 표 하나의 관계가 아니라 "정답 붙은 행 몇 개를 보고 새 행의 결과를 추론하는 방법"을 익힌다.[^tabpfn]

여러 유형의 연습문제를 풀며 푸는 요령을 익힌 학생에 비유할 수 있다.
실제 문제가 연습문제와 비슷한 구조라면 처음 보는 문제도 잘 푼다.
반대로 실제 데이터의 관계가 사전분포가 거의 만들지 않는 모양이라면 성능이 떨어질 수 있다.<Sidenote>초기 TabPFN의 한 체크포인트를 1차원·2차원 분류 문제로 시험한 분석에서는 훈련 데이터의 주기적 패턴을 따라가지 못했다.[^tabpfn-analysis] 초기 가중치의 관찰이지만, 사전분포가 잘 만들지 않는 관계에서 약해질 수 있다는 예다.</Sidenote>

### 2.2 새로운 표에서의 문맥 학습

새 표의 예시를 입력으로 받아 예측하는 방식을 **문맥 학습**(in-context learning)이라 한다.
챗봇에 "사과 → apple, 하늘 → sky" 같은 예시 몇 쌍을 보여 주고 "바다 →"를 물으면, 가중치를 바꾸지 않고도 예시의 형식을 따라 답한다.
TabPFN에서는 정답이 붙은 훈련 행이 예시 쌍이고, 정답을 모르는 행이 새 질문이다.

예측할 펭귄의 행은 훈련 행들을 똑같이 참고하지 않는다.
관련이 깊어 보이는 행을 더 크게 참고하고, 이렇게 입력의 다른 부분에 참고 비중을 나눠 주는 계산을 **attention**이라 한다.
TabPFN은 attention을 여러 층 쌓은 신경망 구조인 트랜스포머(Transformer)로 만들었다.
무엇을 관련이 깊다고 볼지, 예를 들어 날개 길이가 비슷한 행인지 같은 종인 행인지는 사람이 정하지 않고 사전학습에서 익힌 가중치가 정한다.

작은 예로, 훈련 행 두 개가 각각 날개 길이 180 mm에 몸무게 3,500 g, 220 mm에 5,000 g이고 새 펭귄의 날개 길이가 200 mm라고 하자.
두 훈련 행은 날개 길이와 몸무게를 함께, 새 행은 날개 길이만 넣는다.
TabPFN v2에 실제로 넣으면 몸무게 분포의 중앙값은 3,502 g, 10–90백분위는 3,483–4,998 g이었다.
두 점을 잇는 직선(200 mm에서 4,250 g)을 가정하지 않고, 문맥의 두 몸무게를 근거로 예측을 분포로 낸 것이다.

챗봇 비유에는 한계가 있다.
챗봇은 사람의 글로 사전학습해 "사과"의 뜻을 알지만, TabPFN은 합성 표만 보았으므로 "펭귄"이나 "몸무게"가 무엇인지 모른다.
열 이름이 아니라 값들이 함께 변하는 패턴만 본다.

문맥 학습은 **미세조정**(fine-tuning)과 다르다.
미세조정은 사전학습한 가중치를 새 데이터의 손실로 조금 더 갱신하지만, 문맥 학습은 가중치를 그대로 둔다.
TabPFN은 기본적으로 문맥 학습으로 쓰고, 필요하면 미세조정도 할 수 있다.[^tabpfn]
그래서 코드의 `fit(X_train, y_train)`은 이름과 달리 가중치를 갱신하지 않는다.
훈련 행을 저장하고 입력 전처리를 준비할 뿐이며, `predict(X_valid)`를 부를 때 저장한 훈련 행과 검증 행이 함께 신경망을 통과한다.
TabPFN은 예측할 때마다 훈련 행 전체를 문맥으로 처리하므로 훈련 행이 많아질수록 예측이 비싸진다.

정답을 언제 보여 주는지도 단계마다 다르다.

| 단계 | 모델에 들어가는 정보 | 정답의 쓰임 |
|---|---|---|
| 사전학습 | 합성 표의 훈련 행, 가린 행의 특성 | 가린 정답으로 손실을 계산해 가중치 갱신 |
| 새 표에서 예측 | 이 표의 훈련 행(특성과 정답), 예측할 행의 특성 | 훈련 행의 정답만 문맥으로 들어간다 |
| 성능 평가 | 없음 | 검증·테스트 행의 정답은 예측이 끝난 뒤 채점에만 쓴다 |

검증·테스트 행의 정답이 문맥에 섞이면 [09a §1.2](/lecture/2026f-applied-data-science/09a-prediction-and-linear-regression#12-훈련-검증-테스트)의 누출과 같은 문제가 생긴다.

## 3. 기존 후보와의 비교

TabPFN도 다른 후보와 같은 조건에서 비교한다.
[09b §2.2](/lecture/2026f-applied-data-science/09b-features-and-regularization#22-교차검증과-선택)와 같은 훈련 239마리와 같은 5폴드 분할을 쓰고, 특성도 같은 넷(날개 길이, 부리 길이, 부리 깊이, 종)을 쓴다.
테스트 103마리는 선택에 쓰지 않고 최종 평가에 남겨 둔다.

전처리 요구는 모델마다 다르다.
선형회귀와 XGBoost에는 종을 표시 변수로 바꿔 넣는다.
TabPFN은 결측값 처리, 범주형 변수 변환, 척도 조정을 내부에서 하므로 종을 문자열 그대로 넣었다.[^tabpfn]
문자열 열은 범주형으로 보고 순서를 무작위로 섞은 정수 코드나 표시 변수로 바꿔 쓰므로, 종 사이에 크기 순서가 생기지 않는다(0·1·2로 바꿔 넣어도 값이 셋뿐이라 범주형으로 추정되어 결과가 같았다).[^repo]
이 내부 전처리도 `fit`에 넣은 행에서 추정하므로, 교차검증에서는 `fit`에 그 폴드의 훈련 부분만 넣는다.

```python
import pandas as pd
from sklearn.model_selection import train_test_split, KFold, cross_val_score
from tabpfn import TabPFNRegressor
from tabpfn.constants import ModelVersion

url = ("https://raw.githubusercontent.com/allisonhorst/palmerpenguins/"
       "main/inst/extdata/penguins.csv")
cols = ["flipper_length_mm", "bill_length_mm", "bill_depth_mm", "species"]
d = pd.read_csv(url).dropna(subset=cols + ["body_mass_g"])
train, test = train_test_split(d, test_size=0.3, random_state=0)
X, y = train[cols], train["body_mass_g"]  # 종은 문자열 그대로

model = TabPFNRegressor.create_default_for_version(ModelVersion.V2, random_state=0)
cv = KFold(5, shuffle=True, random_state=0)
mae = -cross_val_score(model, X, y, cv=cv, scoring="neg_mean_absolute_error")
print(mae.round(0), mae.mean().round(1))  # 폴드별 MAE와 평균
```

TabPFN은 기본 설정 그대로 쓰고 가중치 버전만 v2로 지정했다(이유는 §4).
XGBoost는 깊이(2, 3, 4), 트리 수(50, 100, 200, 400), 학습률(0.03, 0.1)의 조합 가운데 MAE가 가장 작은 것을 골랐는데, 이 선택도 폴드마다 그 훈련 부분 안에서 다시 5폴드 교차검증으로 했다(중첩 교차검증, `GridSearchCV`, `random_state=0`).
결과는 다음과 같다.
시간은 같은 노트북(Apple M3) CPU에서 쟀고, TabPFN은 tabpfn 9.2.0 패키지와 v2 가중치를 썼다.[^penguins]

| 후보 | 5폴드 CV MAE (g) | 폴드 사이 표준편차 (g) | 예측 한 건에 걸린 시간 |
|---|---|---|---|
| 기준 모델(훈련 평균) | 695 | 43 | |
| 선형회귀 | 257 | 29 | 0.0002초 |
| XGBoost | 274 | 35 | 0.0003초 |
| TabPFN v2 | 248 | 28 | 0.28초 |

초매개변수를 하나도 고르지 않은 TabPFN의 오차가 가장 낮았다.
선형회귀보다 평균 9 g 낮고 다섯 폴드 모두에서 2–14 g씩 낮았으며, 튜닝한 XGBoost는 오히려 선형회귀보다 약 17 g 나빴다.

반면 TabPFN의 예측 한 건은 선형회귀보다 천 배 넘게 느렸다.
대부분은 한 번 부를 때 드는 고정 비용이라 103마리를 한 번에 예측해도 0.30초로 거의 같았고, 훈련 행이 수천 개면 몇 초로 늘어난다.
하루에 몇 번 예측하는 용도라면 문제가 안 되지만 초당 수천 건을 처리해야 한다면 부담이 된다.

SHAP으로 설명할 때는 이 비용이 더 커진다.
트리 구조를 이용하는 빠른 계산을 쓸 수 없어 Kernel SHAP 같은 모델 무관 방법([09c §4.1](/lecture/2026f-applied-data-science/09c-shapley-and-shap#41-kernel-shap))으로 특성을 가린 조합마다 예측을 다시 해야 하므로, 설명할 펭귄 수와 배경 데이터 크기를 작게 잡는다.

## 4. 버전과 이용 조건

TabPFN v2 논문은 예측 속도와 메모리를 스스로 한계로 밝혔다.[^tabpfn]
그 뒤로 더 큰 표를 겨냥한 TabPFN-3과 3.5가 나왔지만 가중치가 비상업 라이선스라, 이 노트는 동의 없이 내려받아 누구나 재현할 수 있는 v2를 썼다.
어느 버전이든 벤치마크의 우위가 프로젝트 데이터에서도 나오는지는 다른 후보와 같은 분할, 같은 계산 예산으로 직접 확인한다.
결과와 함께 패키지와 실제로 불러온 가중치의 버전, 그리고 로컬에서 돌렸는지 외부 서비스를 불렀는지를 남긴다.
외부 서비스를 쓰면 데이터가 밖으로 나가므로 공개할 수 없는 자료에는 실행 위치부터 정한다.
